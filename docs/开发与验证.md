# 开发与验证

本文面向要审计、二次开发或复现验证的读者。普通安装和使用请看 [README](../README.md)。

当前基线是 `0.1.0-beta.1`。支持组合为 Windows x64 Desktop 与 macOS Apple Silicon Desktop 的 `0.2.1-rc.2`/`rc.3`，以及 Linux x64 CLI/Web 的 `0.2.1-rc.2`/`rc.3`/`rc.4`；外部程序基线为 `grok-search-rs` `0.1.26`。每个组合验证了什么见 [支持矩阵](../support-matrix.json)，每次运行的 runId 见 [CHANGELOG](../CHANGELOG.md)。

## 单包结构

公开 Beta 只有一个 npm 包 `dsh-grok-search`。包内 patch 插入一个裸包名聚合组件，
其根 fiber 管理六个子组件：

| 组件 | 包入口 | 职责 |
|---|---|---|
| `grok-search-program` | 根聚合组件内部 | 自动发现/校验已有程序，缺失才准备 profile 私有程序缓存 |
| `grok-search-core` | `dsh-grok-search/search-core` | 注册 `grok-search` provider，统一路由/查询执行器和释放 barrier |
| `grok-search-control` | `dsh-grok-search/control` | 读取 bundle 选择，建立版本化控制记录，临时接管搜索路由 |
| `grok-search-settings-ui` | `dsh-grok-search/settings-ui` | 安全 Cordis Service RPC、共享配置与诊断；详情 slot 内完整 v74 视图 |
| `grok-search-route-verifier` | `dsh-grok-search/route-verifier` | 读取实际搜索、fetch、依赖和原始搜索计数，生成路由验证回执 |
| `grok-search-recovery` | `dsh-grok-search/recovery` | 在下次启动时补完已经提交但未完成的显式释放 |

子组件同属一个聚合 fiber。用户在 PluginManager 中只操作 `dsh-grok-search`。
目标宿主客户端扫描忽略包子路径，因此根入口必须是裸包名，不能只加载 `/bundle`。
独立 recovery 包和额外停止按钮均不属于新体验版。

## 搜索链路

模型继续调用 DSH 官方 `web_search`。插件注册的 `grok-search` provider 接住请求后：

1. 在 release barrier 中登记本次查询。
2. 由 `createSearchExecutor` 排队或启动查询。
3. 主搜开启时懒启动并复用受管原生 Grok 的 stdio MCP；Grok 关闭/失败时，
   有限来源适配器按共享顺序调用补充来源 HTTP API。
4. 校验 Grok 返回的结构，过滤非法 URL，按 URL 去重，并限制结果大小。
5. 返回真实结果并保留内部路由诊断。全部来源失败才明确报错，绝不调用官方搜索。

DSH 的 `fetchProvider`、普通聊天和其他插件依赖不经过本插件的搜索执行器。

### 查询配置

| 字段 | 默认值 | 约束 |
|---|---|---|
| `executable` | 空字符串 | 可选已有原生程序路径；普通用户自动发现，不必填写 |
| `executableArgs` | `[]` | 启动参数数组，不应包含密钥 |
| `configPath` | 空字符串 | 可选配置路径；优先此字段、`GROK_SEARCH_CONFIG`、上游用户目录默认值 |
| `budgetMs` | `120000` | 30000 到 120000 毫秒，包含排队和本地回收 |

容量和大小边界：

- 一个 DSH 实例最多 1 个活动查询、8 个排队查询；外层队列覆盖 Grok 和仅补充模式。
- 同一个总截止包含排队、主搜与全部回退，预留 2000 毫秒回收；回退不另获完整预算。
- 单个 query 按共享 `response_max_chars` 限制最终序列化字符，默认 45000、
  最低导入值 100、本地安全上限 500000；内部诊断为非枚举元数据。
- 这不是 DSH 多 query 合并后或模型面对的 Markdown 格式化总上限。
- 单条 MCP 消息最多 1 MiB。
- 取消、超时和 dispose 只会操作插件自己持有的子进程。
- 进程回收失败时暂停新查询，直到确认退出。
- MCP 配置/环境/程序身份变化先回收再重建；空闲五分钟退出。其他 Agent 的进程不受管理。

### 配置与界面

`src/ui/` 的控制器/CSS/HTML 与本地图标是构建输入，由 `build:client` 内嵌到
`src/client.js`，npm 只分发生成物和运行时代码。详情卡与弹窗分别使用 ShadowRoot，
不污染宿主 body。React effect 管理实例销毁、诊断取消和所有监听/计时器/观察器。

`shared-config` 保留注释和未修改字段，用内容哈希 revision、独占锁、暂存/fsync、
发布前复核及 rename 提交同一份 Grok TOML。密钥和同字段冲突不自动合并。
`preferences` 仅保存 DSH 开关，用独占锁和 revision/CAS，保留未确定提交状态。
两种文件存储均不提供跨资源原子事务或非协作写入者最后瞬间修改的保证。

设置 RPC 由 Cordis Service 注册；后端严格 codec 与客户端描述符来自同一份定义。
插件私有 ALS 捕获 HTTP 原始 socket 事实，必须同时有宿主 owner 和本机/安全传输
证明才能 reveal/提交秘密，不信任客户端自报或转发头。配置历史可含明文秘密，
位置、权限与卸载不清理行为见 README。

### 结果边界

- 只接受 HTTP(S) URL。
- 拒绝带 userinfo 的 URL。
- 按原始 URL 精确去重。
- 超长标题、摘要和正文按序列化预算截断。
- 非法结构、工具错误和协议错误不会伪装成「没有搜索结果」。

主要错误码：

| 前缀 | 含义 |
|---|---|
| `GROK_PROGRAM_MISSING`、`GROK_PROCESS_ERROR` | 程序路径或子进程启动问题 |
| `GROK_CONFIG_INVALID`、`CONFIG_PARSE_FAILED` | 无效执行快照、TOML、字段类型、路径或结果预算，不能伪装成未配置 |
| `GROK_MCP_ERROR`、`GROK_PROTOCOL_ERROR`、`GROK_INVALID_RESULT` | MCP 会话或结果结构问题 |
| `GROK_CHILD_EXIT`、`GROK_TIMEOUT`、`GROK_QUEUE_FULL` | 子进程提前退出、超时或容量已满 |
| `GROK_PROCESS_REAP_FAILED` | 已取消进程未按时回收 |
| `GROK_TOOL_ERROR` | Grok 工具返回明确错误 |
| `GROK_SEARCH_FAILED` | 未分类失败在 provider 边界上的统一错误 |
| `CONTROL_*` | 控制记录、路由、释放或恢复失败的诊断码 |
| `CONFIG_*`、`PREFERENCES_*` | 共享配置/私有开关 CAS、锁、未确定提交或恢复失败 |
| `HTTP_*`、`NETWORK`、`TIMEOUT`、`EMPTY` | 来源诊断的明确分类；不是一律 Key 错误 |

## 控制记录与 CAS

控制记录保存在所用 profile 的 `control-intent.records` 目录，用于跨进程保存接管意图和显式释放证据。

记录 envelope 包含：

- `format` 与 `schemaVersion`。
- 单调递增的 `revision`。
- 唯一 `operationId`。
- 前一 revision 的 `previousSha256`。
- 当前意图、owner lease、选择来源和可选的释放证据。

写入是本地文件系统上的协作式 CAS：

1. 调用方读取当前 revision 与 SHA-256。
2. 在独立暂存文件中同步写入下一 revision。
3. 只有持有相同 expected revision 的写入者，才能把暂存文件以独占 hardlink 方式发布为不可变 revision 文件。
4. 另一个写入者基于旧 revision 提交时会得到 `CONTROL_CAS_CONFLICT`。

保证范围：

- 适用于支持 hardlink 的本地文件系统。
- 只协调遵守同一协议的写入者。
- 文件 fsync 不等于 Windows 目录持久性或断电耐久保证。
- 不支持网络文件系统、锁抢占、恶意外部修改或跨机器仲裁。
- 暂存和旧 revision 保留，不自动清理。
- 记录提交只表示记录文件提交，不表示宿主配置或搜索路由已经改变。

损坏、未知版本、BOM、重复 JSON 键、非法 UTF-8、过深嵌套和大小超限都会失败关闭，不猜测修复。旧格式只能通过显式 inspect/migrate 工具导入，启动时不会自动迁移。

## 发布状态与恢复

控制意图的正常状态是 `required` 或 `released`。

### 接管

只有以下条件同时满足时，控制组件才建立接管：

- 当前 bundle 被选择，且组件以合法身份加载。
- 记录不存在，或现有记录允许按当前选择重新接管。
- 没有已确认的停止状态。

控制组件保存原搜索 provider、fetch provider、inject 指纹和 owner lease，然后临时设置搜索 provider。接管不会写永久 selector，也不会修改宿主或 ASAR。

### 显式停止

原生 PluginManager 停用 bundle 是 owner 存活时的显式退出；兼容停止 RPC
不在新 UI 渲染独立按钮。顺序为：

1. 同步 invalidate，拒绝新查询。
2. 有界 drain，等待在途查询结束。
3. CAS 提交释放意图。
4. 恢复原搜索路由。
5. 独立验证搜索、fetch、依赖和计数窗口。
6. CAS 提交 completion revision。

每一步分别报告，不能用记录提交代替路由验证，也不能用 `applied`、PID、时间差或旧 runId 代替验证回执。

普通 dispose、restart、依赖失效和关闭窗口不会授权 release。热停用恢复原路由，
再启用重新接管，无需删除记录。没有 HMR 时如实提示宿主 restart-required。

### 启动补完

如果上一个进程已经提交释放意图，但在路由恢复或 completion 提交前终止，恢复组件会在下次合法启动时补完：

- 只消费原 owner 的合法 lease、原 intent 和独立路由验证结果。
- 不改变成新的接管授权。
- 不补造历史 release。
- 失败时保留原记录并明确报错。

### 原始搜索计数

路由验证使用 DSH Session 的 canonical 事件 `web/deepseek-search-llm-request` 作为原始官方搜索计数来源。适配器只比较事件类型，不读取、保存或上报事件正文。

这个计数能证明官方 `deepseek-official` provider 的派发尝试，不能证明：

- 网络请求成功或失败。
- 搜索结果质量。
- 宿主级 release 完成事件。

两版公开 ASAR 的只读接缝审计没有发现 release 专属完成事件。因此产品释放以复合证据判定：

> 释放意图记录提交 + 路由恢复到记录的作者状态 + fetch/依赖保持 + 相对计数窗口 delta=0 + completion revision。

这不是跨资源事务，也不是宿主专属回执。

## 安全与隐私边界

- 主搜由受管 Grok 联网；仅补充模式和明确诊断由有限来源 HTTP 适配器联网。
- 程序发现/握手/执行只启动已核验的原生 Grok，使用 `shell: false`。
- 子进程环境只继承系统、代理和已知上游变量，不把整个父进程环境原样传入。
- 后端按需读取共享凭据用于对应请求，普通快照脱敏；显式查看/复制才返回明文。
- 不保存 Grok stderr 原文，避免上游诊断信息泄漏。
- 不改宿主/ASAR/全局程序；用户主动保存会写所选共享配置，影响同文件的其他客户端。
- 自动测试只用隔离 profile、临时文件和合成 Key；真实费用测试必须单独授权。
- 不使用永久 selector、产品专用启动器或全局 monkey-patch。
- 仓库、包和 Issue 中不应出现 API Key、OAuth Token、完整配置、用户名路径或内部日志。

## 验证门禁

开发环境的 Desktop 门禁使用 Node.js 24+；Linux CLI/Web 门禁使用 Node.js 22+。复验使用官方宿主的隔离副本或隔离 CLI/Web `DSH_HOME`、临时 profile；不修改正式 profile 或宿主文件。

### 离线门禁

```powershell
npm run test:all
```

它依次执行：

- `check`：当前全部 scripts/src/fixtures/test JavaScript 模块语法检查。
- provider/core：15 个测试。
- control/store/recovery/migration：266 个测试，Windows 上 1 个按设计跳过，其余 265 个通过。
- release transaction：13 个测试。
- product wiring 与设置 client/网关测试。
- session-owner/MCP 真实离线子进程、共享配置、程序发现/下载/控制、连接安全、
  来源链/回退及偏好测试；实际数量按本次 execution 记录，不硬编码历史数字。

普通 Node 测试只能证明模块行为，不能替代真实 Desktop 验证。

### 双版 Desktop 门禁

当前目标为 DSH Desktop `0.2.1-rc.2` 和 `0.2.1-rc.3`。先将两个程序路径分别指向对应官方宿主，并设置矩阵变量：

```powershell
$env:DSH_B2_TARGET_VERSIONS = "0.2.1-rc.2,0.2.1-rc.3"
node scripts/b2-product-install.mjs --desktop-rc2 "<0.2.1-rc.2 程序>" --desktop-rc21 "<0.2.1-rc.3 程序>" --product-package "<tarball 绝对路径>"
node scripts/b2-plugin-manager-desktop.mjs --desktop-rc2 "<0.2.1-rc.2 程序>" --desktop-rc21 "<0.2.1-rc.3 程序>" --product-package "<tarball 绝对路径>"
node scripts/b2-control-desktop.mjs --desktop-rc2 "<0.2.1-rc.2 程序>" --desktop-rc21 "<0.2.1-rc.3 程序>" --case product
node scripts/b2-control-desktop.mjs --desktop-rc2 "<0.2.1-rc.2 程序>" --desktop-rc21 "<0.2.1-rc.3 程序>" --case m0-04 --grok-program "<Grok 0.1.26 原生程序>"
node scripts/b2-control-desktop.mjs --desktop-rc2 "<0.2.1-rc.2 程序>" --desktop-rc21 "<0.2.1-rc.3 程序>" --case ux
node scripts/internal-candidate.mjs --desktop-rc2 "<0.2.1-rc.2 程序>" --desktop-rc21 "<0.2.1-rc.3 程序>" --package "<tarball 绝对路径>" --real-grok-executable "<Grok 0.1.26 程序>" --real-grok-config "<Grok 配置>"
```

运行器使用回环端口、隔离 profile 和合成上游。每个 runId 独立保存，源码运行期间
不得改变；使用 tarball 的门禁先核对 receipt/sourceHashes。Windows UI 门禁以官方
default_app+原始 ASAR 隔离启动，避免注册用户 `dsh://`；不冒称 packaged 启动通过。
真实付费 Grok 参数只能在用户授权后提供。

macOS Apple Silicon 使用 [macos-beta-gate.yml](../.github/workflows/macos-beta-gate.yml) 在 GitHub 托管的 `macos-15` arm64 runner 上运行同一组门禁：先在 Windows runner 上打包并核对冻结的 tarball 哈希，再下载并校验官方 macOS 安装包，依次运行干净安装、产品 Desktop、M0-04、Grok（上游为本机模拟服务）和 PluginManager。托管 runner 默认英文界面，而 DSH Desktop 按系统首选语言选择界面语言，所以工作流先把首选语言设为简体中文。

### Linux CLI/Web 门禁

在 Windows 上执行时，脚本通过 WSL Ubuntu 22.04 建立隔离 Linux CLI/Web 环境；需提供与 DSH 宿主使用的 pnpm 11.7.0 入口、pnpm store 和 cache 路径。Windows 路径由脚本映射到 WSL；安装以 `--offline` 复用这些缓存，pnpm 仍可能写入自身锁或元数据，不要把该过程视为对共享 store 的只读冻结：

```powershell
$env:DSH_CLI_WEB_WSL_DISTRO = "Ubuntu-22.04"
node scripts/b3-cli-web.mjs `
  --dsh-cli "<对应 rc2、rc3 或 rc4 的 bin.js>" `
  --dsh-version rc3 `
  --product-package "<tarball 绝对路径>" `
  --grok-linux-archive "<已校验的 Grok Linux x64 tar.gz>" `
  --case full `
  --browser-executable "<Linux Chromium 绝对路径>" `
  --pnpm-entry "<pnpm 11.7.0 的 pnpm.cjs>" `
  --pnpm-store "<pnpm store 路径>" `
  --pnpm-cache "<pnpm cache 路径>"
```

分别以 `rc2`、`rc3` 和 `rc4` 执行。`full` 验证配置重载过渡无官方回退、真实
详情 DOM/共享配置/安全 RPC、原生 PluginManager 热停用/再启用/移除及进程回收。
使用临时 `DSH_HOME`、profile、合成 Key 和 loopback stub，不读取正式 profile、
共享配置或真实凭据。run summary/receipt 扫描个人路径后再分享。

覆盖范围包括：

- 干净安装、安装包完整性、启动和完整重启。
- 搜索、fetch、聊天和既有依赖保持。
- owner 存活时原生 PluginManager 显式停用与真实详情操作。
- 普通 dispose 不释放，停用和重新启用按当前选择处理。
- 配置重载后重新接管，以及过渡期无官方搜索回退。
- PluginManager 安装、启用、停用、移除和重启清理。
- M0-04 多 Session、preset、PTC、旧连接、WebSocket 重连和预算矩阵。
- 搜索失败明确报错，不自动回退官方搜索。

## 打包与供应链

```powershell
npm run pack:beta
```

打包要求：

- `package.json` 版本为 `0.1.0-beta.1`，且不能是 `private`。
- 白名单只包含运行时代码、`package.json`、`cordis.patch.yml`、`support-matrix.json`、`README.md` 和 `LICENSE`。
- README 中的包内相对链接必须在 tarball 中存在。
- 打包后记录 SHA-256、integrity 和文件列表。
- 再打包一次必须得到相同 SHA-256。
- 依赖审计必须为 0 项。
- 扫描解包内容，确认没有设备路径、用户名、邮箱、Key、Token 或内部日志。

`next`/`latest` 指向同一 Beta，不能把 registry 首发默认行为当成已完成事实。
latest 是裸名安装入口而非稳定版。发布必须在用户审核后单独执行；打包命令
不会推送、创建 tag、上传附件或发布。

## 提交规范

提交采用英文 type/scope、中文摘要与正文，例如：

```text
docs(readme): 重写公开 Beta 用户说明

按用户安装路径重组快速开始、配置、失败行为与已知限制。
```

不要添加 AI 署名。提交消息检查使用：

```powershell
npm run check:commit -- <提交消息文件>
```
